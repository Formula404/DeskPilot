# DeskPilot 大模型语义意图识别模块开发交付说明

## 1. 交付结论

本次已经把 DeskPilot 的主执行链从：

```text
关键词匹配 → 单一 intent → 固定 LangGraph 分支
```

改造成：

```text
冻结 ContextSnapshot
  → 构造轻量 ManagerContext
  → Manager 输出结构化语义理解和委派计划
  → 校验委派 DAG、Agent 边界和循环上限
  → Web / Knowledge / File / Desktop 专业 Agent
  → 领域白名单工具 + 确定性参数/权限/确认校验
  → Observation / Artifact 回流 Manager
  → Manager 统一最终回复
  → Trace、会话摘要和显式记忆策略
```

现在的“意图”不再等于一个功能标签，而是由以下稳定维度组成：

- `domains`：web、knowledge、file、desktop、conversation。
- `operation_classes`：read、search、extract、transform、create、save、update、delete、open、communicate、inspect、approve。
- `goal_summary`：用户自然语言目标摘要。
- `targets`：当前网页、选区、知识库、本地文件、制品、桌面应用、会话或未知对象。
- `constraints`：输出格式、文件名等约束。
- `needs_clarification`：是否必须澄清。
- `unsupported_requirements`：已经理解、但当前能力不支持的部分。
- `confidence`：仅用于观测和评测，不能绕过安全校验。

## 2. 具体干了什么

### 2.1 Manager 语义理解

新增严格的 Pydantic 协议 `IntentUnderstanding`、`ManagerPlan`、`PlannedDelegation`，所有模型输出禁止额外字段，置信度限制在 0 到 1，并校验澄清问题、动作类型和委派是否一致。

Manager 一次理解完整目标，可以同时输出多个 Domain 和多个 Operation，而不是只选一个标签。普通对话由 Manager 直接回答；信息不足时只问一个关键问题；需要执行时生成带依赖的专业 Agent 委派。

### 2.2 Agents as Tools

实现了四个 Manager 可见的专业 Agent：

| Agent | 状态 | 领域工具 |
|---|---|---|
| Web Agent | 已实现 | 页面采集、绑定页面读取、网页总结、HTML 表格导出、结构化卡片导出 |
| Knowledge Agent | 已实现 | 网页/文件/文本入库、查询、回答、编译、检查、审核、重建索引 |
| File Agent | 已实现 | 受控文本制品读取、Markdown 写入、Excel 写入 |
| Desktop Agent | 安全桩 | 当前没有注册桌面能力时返回 `unsupported`，绝不伪装执行成功 |

专业 Agent 不能调用其他专业 Agent，也看不到其他领域工具。Manager 始终保留会话控制和最终回复权。

### 2.3 跨领域委派和制品流

实现 `DelegationRecord`、依赖图环检测、依赖存在性校验、就绪委派选择、上游失败传播和最大委派数限制。

例如：

```text
总结当前网页，存进知识库，再导出 Markdown

delegation_1: Web Agent 总结网页
delegation_2: Knowledge Agent 保存来源和摘要
  depends_on: delegation_1
delegation_3: File Agent 生成 Markdown
  depends_on: delegation_1
```

下游只接收结构化 dependency result、source ref 和 artifact ref，不把任意大文本塞回 Manager 初始上下文。

### 2.4 Provider 结构化输出兼容

实现三档兼容：

```text
native_json_schema
  → OpenAI Structured Outputs / strict JSON Schema

json_mode
  → JSON object
  → Pydantic 校验

plain_json
  → 从普通文本提取单个 JSON object
  → Pydantic 校验
```

`auto` 模式会在 Provider 不支持原生 JSON Schema 时降级到 JSON Mode 或普通 JSON。Provider 已接受格式但返回非法结构时，只进行一次格式修复，避免无限重试。

### 2.5 安全降级

原 `detect_intent()` 仅保留为兼容接口，不再参与正常 LangGraph 路由。模型不可用时，`legacy_rule_fallback()` 只允许少量明确、低风险、单领域任务：

- 明确的当前网页总结。
- 明确的网页表格导出。
- 明确的知识库查询、入库或只读检查。
- 用户明确要求写入非 Secret 记忆。
- Desktop 请求明确返回未支持。

组合任务、模糊指代和高影响任务不会靠关键词猜测，而是要求恢复模型或澄清。

### 2.6 工具注册表安全边界

`ToolDefinition` 现在同时承担 Capability 元数据，新增：

- `domain`
- `output_schema`
- `preconditions`
- `side_effects`
- `allowed_callers`
- `requires_confirmation`
- `timeout_seconds`
- `examples` / `negative_examples`

每次调用都由服务端确定性执行：

1. 工具存在性检查。
2. 调用者身份检查。
3. 输入 JSON Schema 检查。
4. 确认要求检查。
5. 超时控制。
6. 结构化异常转换。
7. 输出 JSON Schema 检查。

Manager 不在任何低层工具的默认 `allowed_callers` 中。中高风险工具不能因为模型声称“用户已经同意”就跳过确认；知识提案审核和重建索引由代码根据原始用户消息、目标 ID 和明确确认短语判断。

### 2.7 上下文工程

新增 `AGENT_CONTEXT_POLICY` 和 `CAPABILITY_CONTEXT_REQUIREMENTS`。Manager 默认只看：

- 当前消息和有限最近会话。
- 会话摘要。
- 浏览器/窗口快照元数据。
- 最近制品引用。
- 可用 Agent 与 Capability 名称摘要。
- 用户偏好。
- 经过预算筛选、Secret 过滤的相关长期记忆引用。

网页正文、文件全文、OCR 原文和完整知识库证据不进入 Manager 初始理解；需要时由对应专业 Agent 在领域边界内加载。每次委派都会根据目标 Agent 和其 Capability 重新构造 ContextBundle，不再把 Manager 的轻量 bundle 原样传给专业 Agent。

### 2.8 可观测性和数据库

`task_runs` 新增：

- `manager_model`
- `manager_prompt_version`
- `intent_schema_version`
- `intent_understanding_json`
- `manager_latency_ms`
- `manager_fallback_reason`
- `delegation_count`

`task_steps` 会记录：

- `manager.understand`
- `manager.clarify`
- `manager.delegate.<domain>` 的实时事件
- 专业 Agent 的低层 tool call
- `specialist.result`
- `manager.synthesize`
- `finalize`

新增 `GET /tasks/{task_id}/trace`，可以查看语义理解、模型/Prompt/Schema 版本、降级原因、延迟、委派数和完整步骤。

### 2.9 设置和界面

后端设置新增：

- Manager 开关、模型、超时。
- 最大委派数和最大 Manager 循环数。
- Structured Output 模式。
- 澄清置信度阈值。
- Web、Knowledge、File、Desktop Agent 的模型、超时和最大工具步数。

前端 AI 设置页已经可以配置 Manager 开关、结构化输出模式、Manager 模型、最大委派数，以及各专业 Agent 的独立模型。专业模型留空时继承主 AI 模型。

### 2.10 评测基础设施

新增 Manager 评测样本格式和以下计算能力：

- Domain Micro F1。
- Operation Micro F1。
- 澄清准确率。
- 委派依赖准确率函数。

自动测试覆盖结构协议、Provider 降级、一次修复、DAG 校验、调用者白名单、参数 Schema、确认门禁、跨领域执行顺序、Manager 汇总、Trace 和评测指标。

## 3. 怎么实现的

### 3.1 正常路径

`graph.py` 的正常路径不再调用 `route_intent()`：

```text
load_task
  → load_snapshot
  → build_manager_context
  → manager
      ├── clarify/respond → finalize
      └── select ready delegation
            → execute_agent_tool
            → manager
  → manager.synthesize
  → finalize
  → memory_policy
  → END
```

Manager 第一轮调用结构化模型生成 `ManagerPlan`。后续 Manager 循环不再重新猜测意图，而是检查委派状态、选择依赖已经完成的任务，所有委派终止后再统一汇总。

### 3.2 专业 Agent Tool Calling

专业 Agent 使用同一个受限 Tool Calling Runner，但传入不同的：

- caller identity。
- allowed tool names。
- prompt version。
- request schema。
- context policy。
- model、timeout 和 max tool steps。

Runner 只拒绝同一个模型响应中参数完全相同的重复工具调用；进入下一轮模型推理后会清空本轮签名，因此允许页面刷新、状态轮询等合法重调用。任务取消后停止新调用，并把每个 tool call 和 observation 写入审计步骤。Knowledge Agent 被明确允许直接返回非空文本答案，避免已有上下文足以回答时被 `no_tool_fallback` 丢弃；其他需要真实副作用的专业 Agent 仍默认要求工具 observation。

### 3.3 模型不可靠、代码兜底

模型只负责语义理解和受限选择，以下内容由代码拥有：

- Agent 注册表和工具白名单。
- 委派数量、依赖合法性和循环上限。
- 工具调用者身份。
- 输入/输出 Schema。
- 风险等级和是否需要确认。
- 浏览器目标绑定。
- 文件允许目录。
- Secret 脱敏和长期记忆拒绝。
- 任务取消。

这保证“模型理解正确”与“动作允许执行”是两个独立判断。

## 6. 面试怎么讲

### 6.1 30 秒版本

> 我把 DeskPilot 从关键词单意图路由重构成了 Manager + Agents as Tools。Manager 用严格 JSON Schema 一次理解多领域目标、对象、约束和澄清需求，再生成带依赖的委派 DAG。Web、Knowledge、File、Desktop Agent 只看到本领域工具，所有工具调用还会在服务端校验 caller、参数 Schema、风险确认、目标绑定、超时和输出。模型不可用时只对明确低风险单领域任务安全降级，组合和高风险任务不猜。整个理解、委派、工具、Observation 和制品链都能从 task trace 还原。

### 6.2 两分钟版本

可以按“问题—方案—难点—结果”讲：

1. 问题：原系统 `detect_intent()` 只能返回一个字符串，组合任务会丢目标，新功能还要改分类器和固定分支。
2. 方案：把稳定语义和具体能力拆开。Manager 只理解 Domain、Operation、Goal、Target、Constraint；具体功能来自 Tool Registry。
3. 编排：Manager 生成 Delegation DAG，专业 Agent 作为工具执行，结果通过结构化引用回流，最终回复仍归 Manager。
4. 安全：模型永远不能决定工具白名单、caller、确认、文件根目录和浏览器目标；这些全部由代码校验。
5. 兼容：原生 Structured Outputs 不可用时降级 JSON Mode/普通 JSON，并做 Pydantic 校验和最多一次修复。
6. 结果：正常主链不再依赖关键词和固定 intent 分支，单元/集成测试覆盖跨领域依赖和安全门禁，Trace 可以直接用于定位问题和面试演示。

### 6.3 常见追问和回答

#### 为什么不用一个越来越大的意图分类器？

因为用户目标可组合，而且 Capability 的增长速度远高于稳定 Domain。把“网页导出 PDF”做成全局标签会迫使分类数据、路由和上下文策略一起膨胀；现在只需给 Web/File Agent 注册新工具并补相关评测。

#### Manager 和 Handoff 有什么区别？

Handoff 会转移对话控制权；这里是 Agents as Tools。专业 Agent 只完成一个结构化委派并返回结果，不接管用户会话、不直接给最终答复，也不能调用其他专业 Agent。

#### 怎样支持一句话多个目标？

`IntentUnderstanding.domains` 和 `operation_classes` 都是列表，`ManagerPlan.delegations` 也是列表。依赖通过 `depends_on` 表示，不再把整句话压缩成一个 intent。

#### “把它保存下来”怎么解析？

ManagerContext 提供有限最近会话、会话摘要、最近 Artifact/Source、当前 Snapshot 和确定性引用解析结果。若两个引用同样合理，`needs_clarification=true`，而不是让模型任选一个。

#### 怎么防 Prompt Injection？

网页、文件、OCR、知识内容和专业 Agent 结果统一视为不可信数据；网页正文不进 Manager 初始理解；专业 Agent Prompt 和 Manager Prompt 分离；最终执行仍经过 Registry 的 caller、Schema 和安全策略。

#### 模型输出 JSON 不合法怎么办？

优先 native JSON Schema；不支持就降级 JSON Mode/普通 JSON；所有结果最终都走 Pydantic。格式错误只修复一次，仍失败则进入有限安全降级，不允许把非法结果直接用于执行。

#### 模型为什么不能自己判断“用户已经确认”？

模型输出不是授权证据。代码会用原始用户消息、具体工具和目标 ID 做确定性判断；比如审核提案必须同时出现明确接受/拒绝词和相同 proposal ID。

#### 怎么保证专业 Agent 不越权？

有两道边界：专业 Agent 只收到本领域 OpenAI tools；Registry 再校验 `allowed_callers`。即使模型伪造另一个工具名，也无法通过 Registry。

#### 跨 Agent 怎么传数据？

通过 `dependency_results`、`source_refs` 和 `artifact path`。Manager 初始上下文不复制网页/文件全文，既减少 Token，也降低外部内容污染 Manager 的风险。

#### 如何避免死循环和重复调用？

有 `max_manager_turns`、`max_delegations`、`max_tool_steps`；Tool Calling Runner 会拒绝同一模型响应内的同参数重复调用，但允许后续模型轮次为了刷新状态再次调用相同工具。任务取消后不再开始新调用。

#### 为什么 Manager 有记忆但没有完整知识库结果？

长期偏好和事实记忆用于解析“我的笔记应用”这类指代，所以 Manager 会收到经过预算和 Secret 过滤的少量记忆引用。完整知识证据体积大且属于外部不可信数据，按设计不进入 Manager；委派 Knowledge Agent 时会按 `agent:knowledge` 重建上下文，并由 `knowledge.search` / `knowledge.answer` 获取带来源证据。这是在可解释性、Token 成本和 Prompt Injection 风险之间做的边界划分。

#### 模型不调用工具就回答，系统怎么判断？

这不是全局放行。Knowledge Agent 可以基于已给上下文返回非空文本，并记录 `answered_without_tool`；Web、File 等需要读取真实状态或产生副作用的 Agent 默认仍要求成功 observation。这样既保留上下文直答，也不让写文件等动作只靠模型口头声称完成。

#### 旧浏览器扩展没有新元数据怎么办？

后端先尝试 `collect_metadata`，旧扩展不支持时回退 `collect_page`。缺失的 `document_id` 可由 tab 和 URL 派生；有页面文本时计算 SHA-256，否则明确记录 `content_hash_unavailable`。所有兼容路径都写入 degraded reason，避免下游把不完整数据当成完整快照。

#### 怎么评测？

分四层：Manager 语义理解、委派选择与依赖、专业 Agent 工具选择和参数、端到端任务完成。代码已经提供 Domain/Operation Micro F1、澄清和依赖评测基础，生产验收还需要用真实 Provider 跑固定集并人工审核失败样本。

#### 当前还有哪些边界？

要诚实说明：

- Desktop Agent 当前是安全桩，因为仓库尚未注册受控 desktop Capability。
- DAG 已能判断所有 ready 节点，但当前 LangGraph 执行器按就绪顺序串行执行；无依赖并行可以作为性能优化，不能以牺牲审计顺序和目标绑定为代价。
- 当前确定性确认支持明确确认短语；如果产品要做“弹窗审批后从检查点恢复”，还需要继续补 approval resolve API 和前端交互。
- 自动测试证明协议、边界和执行链正确，不等于真实模型已经达到设计文档中的 F1 验收线；真实模型、Prompt 和 Provider 必须跑固定评测集。

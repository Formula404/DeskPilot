# DeskPilot 大模型语义意图识别与 Manager 多 Agent 完整设计

## 1. 文档目的

本文档定义 DeskPilot 最终要达到的自然语言理解、任务编排和多 Agent 执行架构。

最终方案不采用“一个功能对应一个全局意图标签”的模式，也不要求每增加一个功能就重新扩充全局分类器。DeskPilot 使用：

> Manager + Agents as Tools + 确定性安全与执行边界

Manager 负责理解用户完整目标、识别目标对象、解析约束、发现缺失信息、拆分跨领域任务、调用专业 Agent，并保持最终回复的所有权。Web、Knowledge、File、Desktop 等专业 Agent 作为 Manager 可调用的受限工具，各自只看到本领域工具和上下文。

本文档直接描述最终系统，不把关键词路由、单意图分类器或固定 LangGraph 分支作为目标架构。

---

## 2. 最终效果

### 2.1 用户表达不再依赖关键词

以下表达应被理解为相同目标：

```text
总结当前网页
帮我消化一下眼前这篇文章
这页主要讲了什么
提炼一下我正在看的内容
```

以下表达虽然都包含“总结”，但必须区分目标：

```text
总结当前网页
  → Web Agent

总结知识库里的 Python 内容
  → Knowledge Agent

总结昨天的会议记录
  → Conversation 或 File Agent，取决于是否提供文件
```

### 2.2 支持多轮指代

```text
用户：这篇文章主要讲什么？
DeskPilot：……
用户：把它保存进知识库，再导出一份 Markdown。
```

Manager 应解析：

- “它”指上一轮绑定的网页或网页总结制品。
- 需要 Knowledge Agent 保存。
- 需要 File Agent 导出 Markdown。
- 两个任务存在数据依赖。

### 2.3 支持组合目标

```text
总结当前网页并导入知识库
```

不能只选一个标签。Manager 应形成：

```text
Web Agent：采集并总结当前网页
  → Knowledge Agent：将来源和摘要写入知识库
  → Manager：汇总执行结果
```

```text
提取当前网页中的表格，翻译表头，然后保存为 Excel
```

应形成：

```text
Web Agent：抽取结构化表格
  → Web Agent 或语言转换能力：翻译表头
  → File Agent：生成 Excel
  → Manager：返回文件制品
```

### 2.4 信息不足时主动澄清

```text
处理一下这个
导出一下
把它发出去
```

Manager 不应猜测高影响目标，而应只提出一个最有信息价值的澄清问题。

### 2.5 能力不足时如实说明

如果用户要求尚未实现的能力：

```text
打开微信并给张三发消息
```

Manager 应区分：

- 意图已经理解。
- 哪部分能力当前可用。
- 哪部分能力当前不可用。
- 是否需要用户补充信息或授权。

不应把未实现任务落回普通聊天并伪装成已经执行。

### 2.6 新增功能不扩大所有全局标签

新增“网页导出 PDF”时：

- 在 Web/File 领域注册新能力。
- 更新对应专业 Agent 的工具说明和评测。
- 增加跨领域端到端测试。
- 不新增 `web_page_export_pdf` 全局意图。
- 不重做所有领域的全局分类数据。

只有新增全新领域时，才增加新的专业 Agent。

## 3. 当前实现与目标差距

当前代码链路：

```text
用户输入
  → detect_intent() 关键词匹配
  → 单个 intent 字符串
  → _route_after_intent() 固定分支
  → 固定节点或部分 Tool Calling
```

当前实现的主要限制：

- `backend/app/agent/intents.py` 使用关键词顺序决定单一意图。
- `backend/app/agent/graph.py` 将单一意图映射到固定节点。
- 组合任务只能命中一个分支。
- 意图和具体功能高度耦合。
- `desktop_app_open` 可以识别但没有对应执行分支。
- 新功能需要修改识别器、图路由、上下文策略和测试。
- 当前系统更接近“意图路由工作流”，不是严格意义上的多 Agent。

最终系统应取消 `detect_intent()` 对真实执行路径的主导地位，保留它仅作为模型完全不可用时的有限降级能力。

## 4. 最终架构

### 4.1 总体链路

```text
用户提交任务
  → 冻结 ContextSnapshot
  → 创建 Session / Turn / Task
  → 构造 ManagerContext
  → 确定性安全预检查
  → Manager Agent
       ├── 直接回复
       ├── 请求澄清
       ├── 调用 Web Agent
       ├── 调用 Knowledge Agent
       ├── 调用 File Agent
       ├── 调用 Desktop Agent
       └── 组合调用多个专业 Agent
  → 专业 Agent 在领域白名单内选择工具
  → 工具执行层进行参数、权限、目标和审批校验
  → Observation / Artifact 返回 Manager
  → Manager 判断是否继续调用其他 Agent
  → Manager 生成统一最终回复
  → 更新会话摘要、审计与反馈数据
```

### 4.2 控制权

Manager 始终保持：

- 当前用户目标的所有权。
- 任务依赖关系的所有权。
- 是否需要继续委派的决定权。
- 最终回复的所有权。

专业 Agent：

- 不接管整段用户会话。
- 不直接向用户输出最终答案。
- 不调用其他专业 Agent。
- 只完成 Manager 委派的本领域任务。
- 返回结构化结果、制品、证据和后续需求。

这属于 Agents as Tools，而不是 Handoff。

OpenAI 对两种编排模式的区分是：

- Handoff：控制权转移给专业 Agent。
- Agents as tools：Manager 保持控制，把专业 Agent 当作有边界的能力调用。

参考：

- [OpenAI Orchestration and handoffs](https://developers.openai.com/api/docs/guides/agents/orchestration#choose-the-orchestration-pattern)

### 4.3 分层结构

```text
┌──────────────────────────────────────────────┐
│                   Manager                    │
│  语义理解 / 澄清 / 拆解 / 依赖 / 最终回复   │
└──────────────┬──────────┬──────────┬─────────┘
               │          │          │
        ┌──────▼───┐ ┌────▼─────┐ ┌──▼────────┐
        │ Web Agent│ │Knowledge │ │ File Agent│ ...
        │          │ │  Agent   │ │           │
        └──────┬───┘ └────┬─────┘ └──┬────────┘
               │          │           │
        领域工具白名单  领域工具白名单  领域工具白名单
               │          │           │
        ┌──────▼──────────▼───────────▼────────┐
        │  Tool Registry / Safety / Approval   │
        │  参数校验 / 目标绑定 / 审计 / 执行   │
        └───────────────────────────────────────┘
```

## 5. 不再把“意图”设计成功能标签

最终系统区分五个概念。

### 5.1 Domain

稳定的能力领域：

```text
web
knowledge
file
desktop
conversation
```

Domain 数量应保持较少。新增同领域工具不增加 Domain。

### 5.2 Operation Class

稳定的用户操作类型：

```text
read
search
extract
transform
create
save
update
delete
open
communicate
inspect
approve
```

Operation Class 用于理解和审计，不直接映射具体工具。

### 5.3 Goal

用户自然语言目标，例如：

```text
总结当前网页
把结果保存进知识库
导出为 Markdown
打开指定应用
```

Goal 可以保留为自然语言摘要，不需要把所有未来目标变成全局枚举。

### 5.4 Capability

系统可执行的具体能力，例如：

```text
browser.collect_current_page
browser.export_table_to_xlsx
knowledge.ingest_current_page
knowledge.answer
file.write_markdown
desktop.open_application
```

Capability 通过工具注册表动态扩展。

### 5.5 Execution Policy

代码定义的执行边界：

- 必要上下文。
- 风险等级。
- 是否需要确认。
- 参数 Schema。
- 允许调用者。
- 超时和重试。
- 目标绑定要求。

模型不能修改 Execution Policy。

## 6. Manager 的语义理解结果

### 6.1 IntentUnderstanding

Manager 对当前用户请求形成结构化理解：

```python
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field


DomainName = Literal[
    "web",
    "knowledge",
    "file",
    "desktop",
    "conversation",
]


OperationClass = Literal[
    "read",
    "search",
    "extract",
    "transform",
    "create",
    "save",
    "update",
    "delete",
    "open",
    "communicate",
    "inspect",
    "approve",
]


class TargetReference(BaseModel):
    model_config = ConfigDict(extra="forbid")

    kind: Literal[
        "current_browser_page",
        "browser_selection",
        "knowledge_base",
        "local_file",
        "artifact",
        "desktop_application",
        "conversation",
        "unknown",
    ]
    reference_id: str | None
    description: str


class UserConstraint(BaseModel):
    model_config = ConfigDict(extra="forbid")

    name: str
    value: str


class IntentUnderstanding(BaseModel):
    model_config = ConfigDict(extra="forbid")

    schema_version: int
    domains: list[DomainName]
    operation_classes: list[OperationClass]
    goal_summary: str
    targets: list[TargetReference]
    constraints: list[UserConstraint]
    needs_clarification: bool
    clarification_question: str | None
    unsupported_requirements: list[str]
    confidence: float = Field(ge=0, le=1)
```

`goal_summary` 是对用户目标的简短归纳，不是隐藏推理过程。

### 6.2 组合任务示例

输入：

```text
总结当前网页并导入知识库，再保存一份 Markdown。
```

语义理解：

```json
{
  "schema_version": 1,
  "domains": ["web", "knowledge", "file"],
  "operation_classes": ["read", "transform", "save", "create"],
  "goal_summary": "总结当前网页，将来源和摘要保存到知识库，并生成 Markdown 文件",
  "targets": [
    {
      "kind": "current_browser_page",
      "reference_id": "snapshot_xxx",
      "description": "用户提交任务时绑定的浏览器页面"
    }
  ],
  "constraints": [
    {"name": "file_format", "value": "markdown"}
  ],
  "needs_clarification": false,
  "clarification_question": null,
  "unsupported_requirements": [],
  "confidence": 0.91
}
```

### 6.3 置信度

模型返回的 `confidence` 只是观测字段，不是真实概率。

系统不得只因为模型返回高置信度就跳过：

- 能力检查。
- 参数校验。
- 用户确认。
- 工具白名单。
- 目标绑定校验。

低置信度阈值必须通过评测集校准。

## 7. Manager 可见的专业 Agent 工具

Manager 不直接看到所有低层工具，只看到少量稳定的专业 Agent 工具。

### 7.1 Web Agent Tool

```python
class WebAgentRequest(BaseModel):
    objective: str
    snapshot_id: str
    selection_required: bool
    expected_output: str
    input_artifact_refs: list[str]
```

能力：

- 采集任务绑定网页。
- 总结、翻译和整理网页。
- 抽取表格、列表和卡片。
- 生成结构化网页数据。
- 返回网页来源和内容制品。

可见低层工具示例：

```text
browser.collect_current_page
browser.export_table_to_xlsx
browser.export_structured_blocks_to_xlsx
browser.summarize_current_page
```

### 7.2 Knowledge Agent Tool

```python
class KnowledgeAgentRequest(BaseModel):
    objective: str
    source_refs: list[str]
    query: str | None
    proposal_id: str | None
    expected_output: str
```

能力：

- 保存网页、文本或文件来源。
- 查询知识库。
- 编译知识条目。
- 检查和维护索引。
- 审核知识提案。

可见低层工具示例：

```text
knowledge.ingest_current_page
knowledge.ingest_file
knowledge.ingest_text
knowledge.search
knowledge.answer
knowledge.compile_source
knowledge.review_proposal
knowledge.lint
knowledge.semantic_lint
knowledge.rebuild_index
```

### 7.3 File Agent Tool

```python
class FileAgentRequest(BaseModel):
    objective: str
    source_refs: list[str]
    target_format: str | None
    preferred_filename: str | None
    expected_output: str
```

能力：

- 读取允许的本地文件。
- 写入 Markdown、Excel 等制品。
- 进行受支持格式转换。
- 管理生成制品。

可见低层工具示例：

```text
file.write_markdown
file.write_xlsx
```

后续增加 PDF、DOCX 或其他格式时，只扩展 File Agent。

### 7.4 Desktop Agent Tool

```python
class DesktopAgentRequest(BaseModel):
    objective: str
    application_name: str | None
    target_window_id: str | None
    expected_output: str
```

能力：

- 打开已授权应用。
- 定位窗口。
- 执行结构化桌面动作。
- 在结构化能力不可用时使用受控 RPA。

Desktop Agent 未实现前，Manager 必须将相关需求标记为 unsupported，不得假装执行。

### 7.5 专业 Agent 统一输出

```python
class SpecialistAgentResult(BaseModel):
    status: Literal[
        "completed",
        "partial",
        "needs_input",
        "unsupported",
        "failed",
        "cancelled",
    ]
    summary: str
    artifacts: list[dict]
    observations: list[dict]
    source_refs: list[str]
    missing_inputs: list[str]
    unsupported_requirements: list[str]
    suggested_next_actions: list[str]
```

`suggested_next_actions` 只是建议。是否继续委派由 Manager 决定，且仍受服务端策略约束。

## 8. Manager 编排循环

### 8.1 执行逻辑

```text
构造 ManagerContext
  → Manager 理解目标
  → 如需澄清则直接提问
  → 如可直接回答则生成回复
  → 如需执行则调用专业 Agent Tool
  → 接收 SpecialistAgentResult
  → 更新任务依赖和制品引用
  → 判断是否需要其他专业 Agent
  → 所有目标完成后统一回复
```

### 8.2 调用限制

- Manager 每轮最多调用有限数量专业 Agent。
- 同一专业 Agent 的重复调用必须有新的输入或明确纠错目的。
- 达到最大循环次数后返回部分结果和未完成原因。
- 任务取消后不再发起新委派。
- 并行任务只能在不存在数据依赖时并行。
- 跨领域数据通过 `artifact_ref`、`source_ref` 或结构化 Observation 传递，不复制任意大文本。

### 8.3 依赖表示

```python
class DelegationRecord(BaseModel):
    id: str
    agent: Literal["web", "knowledge", "file", "desktop"]
    objective: str
    depends_on: list[str]
    input_refs: list[str]
    status: str
    result_refs: list[str]
```

示例：

```text
delegation_1 Web Agent：总结网页
delegation_2 Knowledge Agent：保存来源和摘要
  depends_on: delegation_1
delegation_3 File Agent：生成 Markdown
  depends_on: delegation_1
```

`delegation_2` 和 `delegation_3` 在 `delegation_1` 完成后可以并行。

## 9. 上下文设计

### 9.1 ManagerContext

Manager 只接收理解和编排所需的轻量上下文：

```python
class ManagerContext(BaseModel):
    current_message: str
    recent_messages: list[dict[str, str]]
    conversation_summary: str | None
    snapshot_summary: dict
    recent_artifact_refs: list[dict]
    available_agents: list[str]
    capability_summary: dict[str, list[str]]
    user_preferences: list[dict]
```

默认不包含：

- 完整网页正文。
- 完整文件。
- 大段 OCR。
- 完整知识库搜索结果。
- 所有低层工具 Schema。

### 9.2 专业 Agent Context

每个专业 Agent 按领域加载上下文：

```text
Web Agent
  → 浏览器快照、选区、网页内容、Web 工具

Knowledge Agent
  → 查询、知识证据、来源引用、Knowledge 工具

File Agent
  → 文件/制品引用、格式要求、File 工具

Desktop Agent
  → 前台窗口、应用 Profile、Desktop/RPA 工具
```

当前 `INTENT_CONTEXT_POLICY` 应改造为：

```text
AGENT_CONTEXT_POLICY
CAPABILITY_CONTEXT_REQUIREMENTS
```

上下文不再依赖越来越细的全局意图标签。

### 9.3 指代解析

Manager 解析：

```text
它
这个
刚才那个
继续
换成 Excel
也保存一下
```

解析依据：

- 最近会话。
- 最近制品。
- 最近来源。
- 当前快照。
- 最近未完成目标。

如果存在两个同等合理引用，必须澄清。

## 10. 新功能扩展方式

### 10.1 工具元数据

每个工具注册：

```python
class CapabilityDefinition(BaseModel):
    name: str
    domain: Literal["web", "knowledge", "file", "desktop"]
    description: str
    input_schema: dict
    output_schema: dict
    risk_level: str
    preconditions: list[str]
    side_effects: list[str]
    requires_confirmation: bool
    examples: list[str]
    negative_examples: list[str]
```

### 10.2 新增同领域功能

例如增加网页导出 PDF：

```text
实现 browser.render_page_to_pdf 或 file.write_pdf
  → 注册 CapabilityDefinition
  → 加入 Web/File Agent 白名单
  → 更新专业 Agent 能力摘要
  → 增加工具参数和领域评测
  → 增加端到端任务测试
```

不修改：

- 全局 Domain 集合。
- Manager 的核心意图标签。
- 其他专业 Agent 的训练或评测数据。

### 10.3 新增全新领域

例如增加邮件和日历：

```text
Communication Agent
Calendar Agent
```

只有出现新的安全边界、上下文类型、工具集合或专业行为时才新增 Agent。

不得因为只有一个新工具就立即拆出一个新 Agent。

### 10.4 Agent 拆分标准

满足多项条件时才拆分：

- 拥有独立工具集合。
- 拥有独立上下文来源。
- 拥有不同安全或审批要求。
- 需要独立提示词和领域知识。
- 单一 Agent 的工具选择评测明显下降。
- 拆分后能在评测中证明质量提升。

## 11. 模型输出与 Provider 兼容

### 11.1 Structured Outputs

Manager 的 `IntentUnderstanding` 和专业 Agent 的结构化结果应优先使用 JSON Schema。

OpenAI Structured Outputs 能保证输出遵循给定 JSON Schema；对于不支持严格 Schema 的 OpenAI 兼容服务，使用 JSON Mode 或普通 JSON，并执行 Pydantic 校验。

参考：

- [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

### 11.2 兼容模式

```text
native_json_schema
  → strict JSON Schema

json_mode
  → JSON object
  → Pydantic 校验

plain_json
  → 提取单个 JSON object
  → Pydantic 校验
  → 最多一次格式修复

provider_failure
  → 安全降级
```

### 11.3 降级行为

模型完全不可用时：

- 明确、低风险、现有规则能够可靠处理的任务可以降级执行。
- 组合任务、模糊任务和高风险任务不使用关键词猜测。
- 不能完整理解时请求用户重试或澄清。
- 记录降级原因。

现有 `detect_intent()` 可以保留为 `legacy_rule_fallback()`，但不能继续作为最终架构的正常路径。

## 12. 安全边界

### 12.1 权限分层

```text
Manager
  只能调用专业 Agent Tools

专业 Agent
  只能调用本领域白名单工具

Tool Registry
  校验工具存在、调用者、参数和风险

Safety / Approval
  校验确认、权限、敏感数据和副作用

Executor
  执行具体动作
```

### 12.2 模型不能决定

- 工具白名单。
- 风险等级。
- 是否跳过审批。
- 文件系统允许根目录。
- 浏览器目标标签页。
- 是否保存 Secret。
- 是否允许任意 Shell、JavaScript 或 RPA。
- 是否接受知识提案。

### 12.3 Prompt Injection

- 用户消息、网页、文件、OCR 和知识内容均为不可信数据。
- Manager 系统规则不能被专业 Agent 结果覆盖。
- 专业 Agent 系统规则不能被网页或文件覆盖。
- 网页正文不进入 Manager 的初始语义理解。
- 所有 Agent Tool 输入经过 Pydantic 校验。
- 所有低层工具调用再次经过 Registry 校验。

### 12.4 高风险操作

以下操作始终由确定性代码要求确认：

- 删除或覆盖文件。
- 重建索引。
- 接受或拒绝知识提案。
- 向外发送消息。
- 桌面 UI 写操作。
- 可能暴露敏感信息的导出。

### 13.1 图结构

```text

  → load_snapshot
  → build_manager_context
  → manager
      ├── clarify

```

现有网页总结、表格导出和知识库节点可以重构为专业 Agent 内部能力，不再作为全局固定意图分支。

## 19. 新功能的测试责任

- 成功结果测试。
- 失败结果测试。

- 专业 Agent 是否能选择新工具。

## 21. 性能与费用

### 21.1 控制模型调用

- Manager 只看轻量上下文和专业 Agent 描述。
- 专业 Agent 只看领域上下文和领域工具。
- 不向任何单个模型暴露所有工具。
- 无依赖的委派可以并行。
- 相同输入和上下文版本可以缓存语义理解。
- 任务取消后停止后续模型调用。

### 21.2 缓存键

```text
current_message_hash
+ recent_context_hash
+ snapshot_capability_hash
+ available_agent_version
+ manager_model
+ manager_prompt_version
```

不能只按当前消息缓存，因为“把它保存下来”依赖会话和目标。

### 21.3 循环上限

```text
max_manager_turns
max_delegations
max_specialist_tool_steps
max_total_model_calls
max_total_tool_calls
```

达到上限时返回：

- 已完成部分。
- 未完成部分。
- 停止原因。
- 是否需要用户继续。

## 22. 失败处理

| 故障 | 最终行为 |
|---|---|
| Manager 超时 | 对简单低风险任务使用 legacy fallback，否则提示重试 |
| Manager 输出非法 | 一次结构修复，仍失败则安全降级 |
| 专业 Agent 超时 | 返回 partial/failed，由 Manager 决定是否重试 |
| 工具不存在 | Specialist 返回 unsupported，不尝试相似高风险工具 |
| 参数非法 | Registry 拒绝，专业 Agent可修正一次 |
| 浏览器不可读 | 明确要求切换 HTTP/HTTPS 页面 |
| 目标已漂移 | 阻止执行并要求重新提交 |
| 文件路径越界 | 阻止执行 |
| 缺少确认 | 转为等待用户确认 |
| Provider 限流 | 有限退避或返回可重试错误 |
| 任务取消 | 所有新委派和工具调用停止 |

## 24. 最终完成定义

系统达到最终目标必须同时满足：

### 语义理解

- 不依赖特定关键词。
- 能理解同义表达和口语。
- 能利用最近对话解析指代。
- 能识别多个同时存在的目标。
- 能提取目标对象和输出约束。
- 信息不足时能够澄清。
- 能区分“已理解但不支持”和“无法理解”。

### 编排

- Manager 始终保持控制权。
- 专业 Agent 作为工具被调用。
- 跨领域任务能表达依赖和并行关系。
- 专业 Agent 不互相直接调用。
- Manager 统一生成最终回复。

### 扩展

- 新增同领域工具不增加全局意图。
- 工具通过元数据注册后进入对应专业 Agent。
- 新增领域才新增专业 Agent。
- 功能扩展只影响相关领域评测和必要端到端测试。

### 安全

- 模型不能扩大工具和文件权限。
- 所有工具参数再次校验。
- 高风险操作确定性审批。
- 浏览器和桌面目标严格绑定。
- Secret 不进入长期记忆和普通审计。

### 质量

- Manager、专业 Agent、工具和端到端均有独立评测。
- 所有关键安全指标为零容忍。
- 模型、Prompt、Schema 和工具版本可追踪。
- 真实错误能够进入人工审核的反馈闭环。

## 25. 设计结论

DeskPilot 最终不再是：

```text
关键词
  → 单一意图标签
  → 固定 LangGraph 分支
```

而是：

```text
Manager 理解完整用户目标
  → 识别多个领域、操作、目标、约束和缺失信息
  → 将专业 Agent 作为受限工具调用
  → 专业 Agent 在领域白名单内选择具体能力
  → 确定性安全层验证并执行
  → Manager 汇总跨领域结果并统一回复
```

这种设计把稳定的语义理解与频繁变化的具体功能分离：

- Manager 关注“用户最终想达到什么结果”。
- 专业 Agent 关注“本领域应该如何完成”。
- 工具注册表关注“系统现在具体能做什么”。
- 安全层关注“什么允许执行、需要什么确认”。
